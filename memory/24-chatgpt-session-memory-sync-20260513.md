## 4. Commercial Product Target

**The commercial .NET product target is NOT a thin parser.**

The target product must:
1. Load a supported format from disk into an **in-memory document object model**
2. Allow **inspection and manipulation** of format-specific entities
3. **Edit** entities (cells, paragraphs, styles, lists, tables)
4. **Save** back to the same format with or without edits
5. **Export/convert** to PDF, PNG, HTML, and related family/type formats (later phases)

### Capability Model (docs/commercial-product-capability-model.md)
| Level | Description |
|-------|-------------|
| C0 | Nothing |
| C1 | File detection only |
| C2 | Streaming metadata/count extraction (Tier 0 parser baseline) |
| C3 | Full document parse, no object model |
| C4 | In-memory object model (read-only DOM) |
| C5 | Object model with inspection API |
| C6 | Object model with edit API |
| C7 | Same-format save after edit (commercial minimum) |
| C8 | Cross-format export (PDF, HTML) |
| C9 | Advanced styling/formatting preservation |
| C10 | Full round-trip fidelity with source format |

**Commercial readiness requires C7+.**

### Current .NET State (as of COMMERCIAL-LOAD-SAVE-VERTICAL-SLICE-SWARM-001)
- Capability: C4-C6-vertical-slice
- FodsDocument.Load/Save, FodsCell.SetText, FodsDocument.Sheets/Rows/Cells
- FodtDocument.Load/Save, FodtParagraph.SetText
- Tests: FODS 42/42 PASS, FODT 43/43 PASS
- commercial_product_ready: false
- Gate 11: NOT approved

**Current .NET source is NOT the full commercial product.** It is a vertical slice demonstrating the correct architecture (DOM-backed XDocument). Full C7 requires broader entity coverage, conversion/export pipelines, and Gate 11 sub-gate evidence.

## 8. AI Usage Policy

**AI is authorized and encouraged as an accelerator. AI is NOT authority.**

### AI is authorized for:
- Retrieval and spec summarization
- Requirements extraction from local normalized spec artifacts
- Object model design proposals
- Code drafting (implementation, tests)
- Test generation (must fail on broken implementation)
- Adversarial review (classified findings only)
- Gap analysis
- Evidence summarization (coordinator verifies all claims)
- Planning and orchestration
- Requirements generation (must be validated before implementation consumes them)

### AI must NOT be used to:
- Approve gates (Gates 1-11 require human approval only)
- Invent unsupported spec claims
- Claim commercial readiness without evidence
- Bypass tests or evidence requirements
- Hide uncertainty
- Send secrets, credentials, or raw copyrighted spec text to external endpoints
- Persist tokens or raw LLM transcripts in the repo
- Commit raw embeddings or vector DB files

### Authority hierarchy (in order):
1. Specs (local cached, normalized)
2. Verified facts (gate evidence, test results)
3. Source code (committed, tested)
4. Deterministic tests
5. Evidence bundles
6. Human decisions (approvals, decisions)
7. Gate records (AGENTS.md, GOVERNANCE.md, registry)
8. AI-generated artifacts (validated only, not raw)

### AI Usage Logging

## 9. AI-Generated Requirements Direction

**Generated requirements are mandatory for commercial format work.**

The system must generate detailed per-format requirements from:
- Local specifications (cached, normalized)
- Format understanding artifacts (schemas/neutral-model/, generated-requirements/)
- Acquisition packs (acquisition-packs/{format}/)
- Existing source/tests
- Product goals (docs/commercial-product-capability-model.md)
- AI retrieval and synthesis
- Schema validation
- Verifier challenge (verifier-review.yaml)

### Requirements Pipeline
```
Format input
→ Format context resolver (local artifacts)
→ Local retrieval (spec chunks, format understanding)
→ AI-generated requirements (YAML with requirement IDs)
→ Schema validation (schemas/requirements/*.schema.json)
→ Verifier review (adversarial challenge)
→ Accepted requirement IDs marked ACCEPTED_FOR_VERTICAL_SLICE
→ Implementation swarm prompt
→ Evidence contract
→ Implementation
→ IV (DEC-034)
→ Capability update
```

**Generated requirements must be validated repo artifacts BEFORE implementation consumes them.**
**Implementation must consume requirement IDs marked `ACCEPTED_FOR_VERTICAL_SLICE`.**

Reference:
- generated-requirements/fods/ — FODS requirements (generated, under review)
- generated-requirements/fodt/ — FODT requirements (generated, under review)
- tools/requirements/ — generation and validation tools
- schemas/ — schemas for requirement validation

## 10. Skill-System Direction

**The repeatable skill system must be a requirements-generation and verification system first, then a prompt generator.**

The skill system must:
1. Accept a format name as input
2. Resolve format context (local artifacts, spec, gates, capabilities)
3. Perform local retrieval (spec chunks, neutral model, acquisition pack)
4. Generate requirements using governed AI
5. Validate generated requirements against schemas
6. Produce a verifier review (adversarial challenge)
7. Accept requirement IDs for the implementation slice
8. Generate an implementation swarm prompt (not a bare chatgpt prompt)
9. Attach an evidence contract to the swarm
10. Hand off to implementation
11. Then IV
12. Then capability update

The skill is NOT just a template-filler. It is a governed, evidence-producing pipeline.
