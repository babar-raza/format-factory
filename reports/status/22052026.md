## How the system acquires and processes a format

In simple terms, the system should work like this:

### 1. Find the official source

For a format, the system first asks: where is the real truth?

For example:

* official specification,
* RFC,
* ODF standard,
* vendor documentation,
* known sample corpus,
* format reference files.

The system should not trust random blog posts or AI guesses as authority.

### 2. Cache or record the source

If the spec can be cached locally, it goes into a local spec cache. If it cannot be committed for licensing reasons, the system records metadata instead:

* source URL,
* version,
* hash,
* date acquired,
* legal/redistribution status,
* whether local cache exists.

This is important because future agents should not “rediscover” the format every time.

### 3. Collect samples

The system needs real files to test against. These samples must also have provenance:

* where did the sample come from?
* is it synthetic or real?
* can it be redistributed?
* what is its hash?
* which tests use it?

This is the phase we are now auditing more deeply.

### 4. Convert specs and samples into requirements

The system turns the spec/sample knowledge into concrete requirements:

* what the parser must read,
* what fields matter,
* what errors must be handled,
* what security cases matter,
* what features are in scope or out of scope.

AI can help summarize, but the final accepted requirements must be validated by tests and evidence.

### 5. Build parser/prototype

The parser reads the format and turns it into a neutral internal model. The neutral model is important because it lets Python and .NET share the same conceptual behavior.

For example, a spreadsheet-like format might become:

```text
Workbook
  Sheets
    Rows
      Cells
        value
        value_type
        formula
```

### 6. Test parser and security behavior

The system checks:

* valid files parse,
* bad files fail safely,
* malformed files do not crash,
* dangerous paths are not extracted,
* compressed formats have limits,
* fuzz tests do not break parser assumptions.

### 7. Build writer/exporter where allowed

For some formats, reading is enough at first. For stronger product readiness, the system adds writing/exporting:

* save back to same format,
* export to CSV/TXT/HTML/JSON,
* preserve typed values,
* preserve formulas,
* preserve paragraphs/headings/tables, etc.

### 8. Build Python and .NET products

The system then packages the implementation:

* Python wheel,
* Python source distribution,
* .NET NuGet package.

This is where we are now with FODS/FODT. The packages exist, but the final validation/consumer proof needs one more strong cleanup.

### 9. Prove packages from outside the source tree

This is critical. A package is not really proven if it only works inside the repo.

The final proof should be:

* install Python wheel in a clean environment,
* run smoke tests from the installed package,
* restore NuGet package in a clean consumer project,
* run real consumer code,
* prove artifacts in the bundle match hashes.

R47 got closer, but this still needs clean closeout.

## Is it generic?

**Yes, the design is generic.**

The system is not hardcoded only for FODS/FODT. It already has many formats in the registry and sample folders. The workflow can be reused for future formats.

But “generic” does not mean “every future format is automatic.” File formats differ a lot.

A simple format like PPM, PBM, PGM, CSV, TSV, or ZST can move faster.

A complex format like XCF, ODS, ODT, FODP, FODG, or Gnumeric needs more careful handling because it may involve:

* complicated internal structure,
* compression,
* XML,
* binary chunks,
* embedded resources,
* security risks,
* licensing/sample issues,
* many optional features.

So the honest answer is:

```text
The pipeline is generic.
The effort per format will vary.
Simple formats should be easy.
Complex formats still need controlled phase-by-phase work.
```

## 1. What the final Python/.NET products must do

Your product requirement should be stated like this:

| Requirement      | Meaning                                                                         |
| ---------------- | ------------------------------------------------------------------------------- |
| Parse/load       | Open a real file and build an in-memory model.                                  |
| Edit             | Change a meaningful object based on document type.                              |
| Save same format | Write back to the original format.                                              |
| Preserve         | Keep untouched content as close to original as possible.                        |
| Export           | Save to other formats later, preferably using our own Format Factory libraries. |

So for a spreadsheet-like format such as FODS:

```text
Load workbook
→ access sheet/cell/style/formula
→ edit cell value/style/formula
→ save as FODS
→ reload saved FODS
→ verify changed cell
→ verify unchanged cells/styles/formulas survived
```

For a document-like format such as FODT:

```text
Load document
→ access paragraphs/headings/runs/styles/alignment/font info
→ edit heading text/font/size/alignment
→ save as FODT
→ reload saved FODT
→ verify edit
→ verify other paragraphs/styles/tables survived
```

That is stronger than what the current system has mostly proven so far.

## 2. Object model is the right direction

I agree with your instinct: **object model first** is the correct architecture.

A parser-only approach is too weak. If we only parse into loose dictionaries, future editing becomes fragile. For production, the system needs a stable in-memory model.

The better architecture is:

```text
Original file
   ↓
Parser
   ↓
Object model / DOM-like model
   ↓
Editing API
   ↓
Writer / serializer
   ↓
Saved same-format file
   ↓
Reload verification
```

For spreadsheets, the model should look roughly like:

```text
Workbook
  Sheets
    Rows
      Cells
        address/name
        value
        value_type
        formula
        style
          font
          fill
          border
          number_format
          alignment
```

For documents:

```text
Document
  Sections
    Blocks
      Paragraph
      Heading
      Table
      List
    Runs
      text
      style
      font
      size
      bold/italic
      alignment
```

This object model gives you future agility. New features become additions to the model and writer, not rewrites of the whole parser.

## 3. Same-format save is the hardest requirement

This is the big one.

“Save same format while preserving everything else” can be done at different quality levels:

| Level   | Meaning                                                                     |
| ------- | --------------------------------------------------------------------------- |
| Level 1 | Parse and regenerate a simplified file.                                     |
| Level 2 | Preserve major structures and content.                                      |
| Level 3 | Preserve styles, metadata, formulas, tables, and layout-sensitive features. |
| Level 4 | Near round-trip fidelity with unknown/unsupported content preserved.        |
| Level 5 | Production-grade compatibility.                                             |

For POC, we should require at least:

```text
Level 2+ for FODS/FODT:
major content preserved,
edited item changes correctly,
known styles/formulas/metadata preserved where claimed,
unsupported features not silently destroyed without warning.
```

For production, we need a preservation strategy.

The best design is probably a hybrid:

```text
Object model for known/editable features
+
raw preservation layer for unknown/unmodified XML/nodes/parts
```

That means:

* known things can be edited through the object model,
* unknown things are carried through untouched where possible,
* the writer does not flatten the whole file unnecessarily,
* preservation is measurable through tests.

This matters especially for ODF-family formats like FODS/FODT.
