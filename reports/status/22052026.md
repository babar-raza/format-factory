## What the system does well now

The system is good at **not trusting claims blindly**. That is important. It now has registries, taskcards, evidence bundles, phase audits, tests, validators, package manifests, and state snapshots. This means an agent cannot simply say “done” without leaving evidence.

It is also good at moving a format through a repeatable pipeline. For FODS and FODT, the system can already:

1. track the format in a registry,
2. connect it to requirements,
3. run parser/writer tests,
4. build Python wheels and source packages,
5. build .NET NuGet packages,
6. bundle proof artifacts,
7. run evidence checks,
8. keep AI as helper only, not authority.

R47 was a major step because it finally included real package files in the evidence bundle: Python wheels, Python source packages, and .NET `.nupkg` files. Before that, reports claimed packages existed, but the uploaded bundle did not actually contain them.

The main repeatability weakness is not the core code now. It is **agent closeout discipline**. The agent keeps doing real work, then forgets to refresh the final verdict/proof after bundle validation. That creates contradictions like:

```text

```

That is not a product-code problem. It is a process-closeout problem, and it must be fixed with a hard closeout script/skill.

## How the system acquires and processes a format

In simple terms, the system should work like this:

### 1. Find the official source

For a format, the system first asks: where is the real truth?

For example:

* official specification,
* RFC,
* ODF standard,
* vendor documentation,
* known sample corpus,
* format reference files.

The system should not trust random blog posts or AI guesses as authority.

### 2. Cache or record the source

If the spec can be cached locally, it goes into a local spec cache. If it cannot be committed for licensing reasons, the system records metadata instead:

* source URL,
* version,
* hash,
* date acquired,
* legal/redistribution status,
* whether local cache exists.

This is important because future agents should not “rediscover” the format every time.

### 3. Collect samples

The system needs real files to test against. These samples must also have provenance:

* where did the sample come from?
* is it synthetic or real?
* can it be redistributed?
* what is its hash?
* which tests use it?

This is the phase we are now auditing more deeply.

### 4. Convert specs and samples into requirements

The system turns the spec/sample knowledge into concrete requirements:

* what the parser must read,
* what fields matter,
* what errors must be handled,
* what security cases matter,
* what features are in scope or out of scope.

AI can help summarize, but the final accepted requirements must be validated by tests and evidence.

### 5. Build parser/prototype

The parser reads the format and turns it into a neutral internal model. The neutral model is important because it lets Python and .NET share the same conceptual behavior.

For example, a spreadsheet-like format might become:

```text
Workbook
  Sheets
    Rows
      Cells
        value
        value_type
        formula
```

### 6. Test parser and security behavior

The system checks:

* valid files parse,
* bad files fail safely,
* malformed files do not crash,
* dangerous paths are not extracted,
* compressed formats have limits,
* fuzz tests do not break parser assumptions.

### 7. Build writer/exporter where allowed

For some formats, reading is enough at first. For stronger product readiness, the system adds writing/exporting:

* save back to same format,
* export to CSV/TXT/HTML/JSON,
* preserve typed values,
* preserve formulas,
* preserve paragraphs/headings/tables, etc.

### 8. Build Python and .NET products

The system then packages the implementation:

* Python wheel,
* Python source distribution,
* .NET NuGet package.

This is where we are now with FODS/FODT. The packages exist, but the final validation/consumer proof needs one more strong cleanup.

### 9. Prove packages from outside the source tree

This is critical. A package is not really proven if it only works inside the repo.

The final proof should be:

* install Python wheel in a clean environment,
* run smoke tests from the installed package,
* restore NuGet package in a clean consumer project,
* run real consumer code,
* prove artifacts in the bundle match hashes.

R47 got closer, but this still needs clean closeout.

## Is it generic?

**Yes, the design is generic.**

The system is not hardcoded only for FODS/FODT. It already has many formats in the registry and sample folders. The workflow can be reused for future formats.

But “generic” does not mean “every future format is automatic.” File formats differ a lot.

A simple format like PPM, PBM, PGM, CSV, TSV, or ZST can move faster.

A complex format like XCF, ODS, ODT, FODP, FODG, or Gnumeric needs more careful handling because it may involve:

* complicated internal structure,
* compression,
* XML,
* binary chunks,
* embedded resources,
* security risks,
* licensing/sample issues,
* many optional features.

So the honest answer is:

```text
The pipeline is generic.
The effort per format will vary.
Simple formats should be easy.
Complex formats still need controlled phase-by-phase work.
```

## Can it handle more future formats with few changes?

For many future formats, yes.

The system should be able to add a new format by adding or updating:

1. registry entry,
2. spec/provenance record,
3. sample provenance,
4. generated requirements,
5. parser/prototype,
6. tests,
7. package mapping,
8. evidence contract.

For simple formats, this could become a mostly repeatable process.

For complex formats, it will still need format-specific work, but the **control framework** will stay the same. That is the important win. We are building a factory, not hand-building every product from scratch.

## Can we test it phase by phase?

Yes. This is exactly the right direction now.

Instead of asking “is the whole system good?”, we should test each phase separately. That makes problems easier to find.

The phase sequence should be:

| Phase   | Plain-English meaning                                              | Current strength                                                          |
| ------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Phase 1 | Did we get the right official spec/source?                         | Started; core formats decent; minor formats partial                       |
| Phase 2 | Do we have valid samples and know where they came from?            | Started in R47; incomplete because not all sample folders were covered    |
| Phase 3 | Did we turn specs/samples into parser requirements and prototypes? | Exists for FODS/FODT; needs formal audit next                             |
| Phase 4 | Do parser, neutral model, fuzz/security/oracle tests work?         | Partially strong for some formats; should be audited after Phase 3        |
| Phase 5 | Is the format authorized and mapped to product behavior?           | Exists but must be checked carefully before product claims                |
| Phase 6 | Can we build real packages and prove them from clean installs?     | Almost there for FODS/FODT; R47 fixed artifacts, closeout still defective |
| Phase 7 | Can we approve commercial/publication readiness?                   | Not yet; Gate 11 remains blocked, correctly                               |

This phase approach is the right way to prevent drift. It makes the system prove each layer before trusting the next layer.
