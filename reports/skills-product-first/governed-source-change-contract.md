# Governed Source-Change Contract — Companion Guide
Sprint: FORMAT-FACTORY-SKILLS-PRODUCT-FIRST-GOVERNED-EXECUTION-001
Generated by: TC-W1-002

## Why 5 Tiers?

A flat FAIL_CLOSED enforcement model blocks governance/tooling work that doesn't touch product source.
The 5-tier model separates failure modes by severity, allowing autonomous execution of governance
work (Tier 3-4) while protecting product source (Tier 1-2) and blocking true external gates (Tier 5).

---

## The 5 Enforcement Tiers

### Tier 1: FAIL_CLOSED — Product Source Changes
Applies to: `src/net/*`, `src/python/*`
When: A work item proposes to add or modify product source code.
Enforcement: STOP — only Mainstream-authorized agents with full 9-field packet may proceed.
Autonomous action: Skills lane STOPS and records in coordinator-integration-log.md. Mainstream proceeds.

Required fields: skill_id, format_id, transcript_path, focused_test_raw_log_path, source_diff_path,
allowed_files, forbidden_files, rollback_note, ledger_entry_path.

Downgrade rule: All 9 fields present but capability_matrix_update missing → ACCEPT_WITH_LIMITATIONS
(not a hard FAIL).

### Tier 2: FAIL_WITH_REWORK — Product Tests and Examples
Applies to: `tests/net/*`, `tests/python/*`, `examples/*`
When: A work item proposes to add or modify product tests or examples.
Enforcement: FAIL_NEEDS_REPAIR — produce the test file and raw log, then rerun.
Autonomous action: Repair locally (AUTONOMOUS_REWORK_REQUIRED). No external gate needed.

### Tier 3: YES_WITH_LIMITATIONS — Governance/Tooling/Templates
Applies to: `reports/*`, `docs/prompt-templates/*`, `.supervisor/*` (conditional), `.claude/commands/*` (conditional)
When: A work item creates governance artifacts, templates, or tool configurations.
Enforcement: PROCEED with noted limitations.
Autonomous action: AUTONOMOUS_ALLOWED or GUARDED_AUTONOMOUS_ALLOWED (for registry/command files).

### Tier 4: ACCEPT_WITH_LIMITATIONS — Report-Only Planning
Applies to: Planning documents, state files, docs
When: A work item creates advisory planning artifacts only.
Enforcement: ACCEPT — advisory; note any missing optional fields.
Autonomous action: AUTONOMOUS_ALLOWED.

### Tier 5: BLOCKED_EXTERNAL_GATE — External/Release/Gate Actions
Applies to: git push, package publication, Gate 8/11 approval, credential usage
When: A work item requires action outside the local repo environment.
Enforcement: STOP — record in coordinator-integration-log.md.
Autonomous action: Never attempt. Record blocker and continue with other work.

## How Mainstream Uses This Contract

1. Read the selected gap from `reports/skills-product-first/mainstream-consumption-packet.json`.
2. Identify the enforcement tier for the planned work:
   - Source change → Tier 1 (9 required fields, full packet)
   - Test/example change → Tier 2
   - Governance work → Tier 3
3. Produce all required artifacts for the tier.
4. Run validate_adoption_compliance.py against the work item.
5. Declare evidence in evidence-declaration.yaml.

---

## How Supervisor Grades This Contract

The Supervisor autonomous_cycle.py grades each work item against the 5-tier contract:
- Tier 1 items: All 9 required fields must be present → ACCEPTED or REJECTED
- Tier 2 items: Test files + raw log required → ACCEPTED or FAILED_NEEDS_REPAIR
- Tier 3 items: Governance artifacts present → ACCEPTED_WITH_LIMITATIONS or ACCEPTED
- Tier 4 items: Planning docs present → ACCEPTED (advisory)
- Tier 5 items: Blocker recorded → BLOCKED_EXTERNAL (not a sprint failure)

---

## How Acceleration Avoids False Positives

Acceleration checks Mainstream work items for completeness. With a 5-tier model:
- A missing capability_matrix_update is a DOWNGRADE (Tier 4), not a false FAIL
- A missing ledger_entry_path on a Tier 3 item is a note, not a REJECTED
- Only Tier 1 items require the full 9-field packet

The downgrade rules in the contract YAML specify exactly which omissions are acceptable per tier.
See `governed-source-change-contract.yaml` §downgrade_rules for each tier.

---

## How to Continue After Fixing a Missing Artifact

If your work item is missing a required artifact and was graded FAIL or FAILED_NEEDS_REPAIR:

1. Identify the missing field from the validation error message.
2. Create the missing artifact:
   - Missing transcript → run the skill and produce the transcript JSON
   - Missing raw log → rerun the focused test command and capture output
   - Missing source diff → capture `git diff -- <allowed_files>` to a file
3. Update the work item's `evidence_paths` in evidence-declaration.yaml.
4. Rerun validate_adoption_compliance.py to confirm compliant=true.
5. Rerun autonomous_cycle.py — the item should now be graded ACCEPTED.

Never stop for locally fixable missing artifacts. Always repair and rerun.
