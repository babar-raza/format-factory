## TC-A1: Gate 11 Context-Pack vs Registry Contradiction

### Contradiction Summary

The generated context-pack.yaml (advisory) claims Gate 11 is APPROVED for FODS, FODT, and Netpbm. The authoritative registry says Gate 11 is NOT APPROVED for any format.

### Verbatim Evidence

```yaml
poc_matrix:
  sprint: R114
  last_updated: '2026-06-04'
  commercial_net_products:
    FODS:
      dotnet_tests: 547
      gate_11_status: APPROVED_BY_BABAR_RAZA_2026_06_05
      commercial_ready: false
    FODT:
      dotnet_tests: 520
      gate_11_status: APPROVED_BY_BABAR_RAZA_2026_06_05
      commercial_ready: false
    Netpbm:
      dotnet_tests: 423
      gate_11_status: APPROVED_BY_BABAR_RAZA_2026_06_05
      commercial_ready: false
```

**Source 2: registry/format-registry.yaml (authoritative)**

FODT:

**Source 3: AGENTS.md section D1 (normative)**

**Source 4: docs/gates.md Gate 11 definition (normative)**
> "Gate 11: Commercial Readiness Complete... requires commercial product lead sign-off... registry/format-registry.yaml updated with gate_11_status: passed."

**Source 5: plans/master-plan.md (primary operational authority)**
> "Phase 3+: FODS Gates 1-10 ALL PASSED; Gate 11 commercial_readiness_in_progress"

### Contradiction Analysis

| Field | context-pack.yaml | registry/format-registry.yaml | Winner |
|---|---|---|---|
| FODS Gate 11 status | APPROVED_BY_BABAR_RAZA_2026_06_05 | commercial_readiness_in_progress | **Registry** |
| FODS approved_by | (implied Babar Raza) | null | **Registry** |
| FODT Gate 11 status | APPROVED_BY_BABAR_RAZA_2026_06_05 | commercial_readiness_in_progress | **Registry** |
| Netpbm Gate 11 status | APPROVED_BY_BABAR_RAZA_2026_06_05 | (no gate_11 section) | **Registry** |

### Resolution

**Per authority hierarchy:** Registry is authoritative (Level 2). Context-pack is advisory (Level 8). When they conflict, registry wins.

**Verdict:** Gate 11 is NOT APPROVED for FODS, FODT, or Netpbm. The context-pack.yaml contains stale/incorrect claims. Any downstream system (supervisor, next-sprint generator, continuation signal) that reads context-pack gate_11_status will produce incorrect conclusions.

**Root cause:** The context-pack was likely generated by a supervisor sprint that projected a planned/proposed approval state rather than reading the actual registry. No cross-check validator existed to prevent this overclaim.

**Impact:** Any autonomy continuation that treats Gate 11 as approved will incorrectly bypass the commercial readiness gate. The context-pack must be regenerated or manually corrected. Until corrected, no system should rely on context-pack for gate status.

### Recommended Actions (no code changes in this sprint)
1. Future: Add cross-check validator that reads registry gate_11 fields before writing context-pack gate_11_status
2. Future: Regenerate context-pack.yaml from authoritative sources
3. This sprint: Document contradiction in this report for human review

## TC-A2: Generated-Output Authority Cross-Check Validator Specification

### Problem
Generated files (context-pack.yaml, next-sprint.md, continuation-signal.json) can drift from authoritative state without detection.

### Proposed Validator: `validate_generated_authority.py`

**Inputs:**
- registry/format-registry.yaml (authoritative)
- .supervisor/context-pack.yaml (generated)
- reports/supervisor/next-sprint.md (generated)
- .local/supervisor/continuation-signal.json (generated)

**Checks:**
1. For each format in context-pack poc_matrix:
   - Read gate_11_status from context-pack
   - Read gate_11.status + gate_11.approved_by from registry
   - If context-pack claims APPROVED but registry has approved_by: null → FAIL with "Gate 11 overclaim detected"
2. For next-sprint.md:
   - If any task claims Gate 11 approved → cross-check registry → FAIL if registry disagrees
3. For continuation-signal.json:
   - If advisory_prompt_executable: true but registry shows hard gates pending → FAIL

**Outputs:**
- PASS: all generated claims consistent with registry
- FAIL: list of inconsistencies with verbatim evidence from both sources

**Integration point:** Run before every autonomous-cycle to prevent overclaiming. Add as Step 0 in autonomous_cycle.py pipeline.

**Implementation status:** NOT YET IMPLEMENTED. This is a specification only. Implementation taskcard required for future sprint.

## TC-A3: Authority Rules for Generated State Files

### File Classification

| File | Authority Level | Type | Writable By |
|---|---|---|---|
| AGENTS.md | 1 - Normative | Governance | Human only |
| registry/format-registry.yaml | 2 - Authoritative | Gate status | Human only (gate approvals) |
| docs/gates.md | 3 - Normative | Gate definitions | Human only |
| plans/master-plan.md | 1 - Primary operational | Living plan | Human + agent (with prompt) |
| .supervisor/context-pack.yaml | 8 - Advisory | Generated state | Supervisor pipeline (auto) |
| reports/supervisor/next-sprint.md | 8 - Advisory | Generated prompt | Supervisor pipeline (auto) |
| reports/supervisor/session-resume.md | 8 - Advisory | Generated summary | Supervisor pipeline (auto) |
| reports/supervisor/approval-gates.md | 8 - Advisory | Generated gates | Supervisor pipeline (auto) |
| .local/supervisor/continuation-signal.json | 8 - Advisory | Generated signal | Supervisor pipeline (auto) |
| reports/supervisor/contradictions.md | 8 - Advisory | Generated check | Supervisor pipeline (auto) |
| .local/supervisor/action-queue.jsonl | 4 - Operational | Queue items | Supervisor + agent (governed) |

### Conflict Resolution Rules
1. If any Level 8 file contradicts Level 2 (registry) → Level 8 file is WRONG
2. If continuation-signal claims state that registry does not support → continuation-signal is WRONG
3. If next-sprint.md recommends action that violates AGENTS.md → next-sprint.md recommendation is INVALID
4. Generated files must NEVER override authoritative files
5. Cross-check validator (TC-A2) must run before accepting generated state claims
