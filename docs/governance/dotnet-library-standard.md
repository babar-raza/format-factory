# .NET Library Standard — Format Factory

This document defines the structural, naming, and quality standards for all .NET
libraries in the Format Factory project. Every format library MUST conform to these
rules. Deviations require an explicit waiver recorded in the master plan.

---

## 1. Project Structure

Each format is a separate .csproj under `src/net/{format}/`. The directory layout
MUST follow this canonical structure:

```
src/net/{format}/
  FormatFactory.{Format}.csproj    — project file (required)
  {Format}Parser.cs                — deserialization / loading (required)
  {Format}Document.cs              — domain model, pure data, NO I/O (required)
  {Format}Writer.cs                — serialization / saving (required)
  {Format}*Exporter.cs             — cross-format exporters (zero or more)
  README.md                        — package readme (required for NuGet)
  Model/                           — supporting model classes
  Spec/                            — specification-aligned class hierarchy
  Exceptions/                      — format-specific exception hierarchy
```

### 1.1 Existing Formats (reference)

The following format directories exist under `src/net/`:

| Directory  | Assembly                        |
|------------|---------------------------------|
| `csv`      | `FormatFactory.Csv`             |
| `fods`     | `FormatFactory.Fods`            |
| `fodt`     | `FormatFactory.Fodt`            |
| `html`     | `FormatFactory.Html`            |
| `markdown` | `FormatFactory.Markdown`        |
| `ndjson`   | `FormatFactory.Ndjson`          |
| `netpbm`   | `FormatFactory.Netpbm`          |
| `tsv`      | `FormatFactory.Tsv`             |
| `txt`      | `FormatFactory.Txt`             |
| `zst`      | `FormatFactory.Zst`             |

### 1.2 File Naming

- Parser: `{Format}Parser.cs` — contains all deserialization logic.
- Document: `{Format}Document.cs` — the root domain model class.
- Writer: `{Format}Writer.cs` — contains all serialization logic.
- Exporters: `{Format}{Target}Exporter.cs` — one file per target format.
  Example: `FodsCsvExporter.cs`, `FodsHtmlExporter.cs`, `FodsJsonExporter.cs`.
- Model classes: `Model/{ClassName}.cs` — one class per file.
- Spec classes: `Spec/{SpecNamespace}/{ClassName}.cs` — mirrors spec hierarchy.
- Exceptions: `Exceptions/{Format}DocumentException.cs` (or more specific names).

### 1.3 Spec Directory

The `Spec/` directory contains specification-aligned class hierarchies that mirror
the canonical QName structure from `shared/qname-registry/{format}.yaml`. Files in
`Spec/` MAY be `architecture_only` stubs (generated by `tools/spec/generate_canonical_stubs.py`)
marked with `// GENERATED — architecture_only`. These are intentional spec-parity
markers, NOT behavioral implementations. V48 blocks RELEASE_GATE items from citing
architecture_only stubs as evidence.

## 2. Project File Standards

Every `.csproj` MUST include the following properties:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <AssemblyName>FormatFactory.{Format}</AssemblyName>
    <RootNamespace>FormatFactory.{Format}</RootNamespace>
    <Version>0.1.0-tier0</Version>
    <Authors>format-factory</Authors>
    <Description>...</Description>
    <GenerateDocumentationFile>true</GenerateDocumentationFile>
    <PackageId>FormatFactory.{Format}</PackageId>
    <PackageReadmeFile>README.md</PackageReadmeFile>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <AllowUnsafeBlocks>false</AllowUnsafeBlocks>
    <TreatWarningsAsErrors>false</TreatWarningsAsErrors>
  </PropertyGroup>

  <ItemGroup>
    <None Include="README.md" Pack="true" PackagePath="/" />
  </ItemGroup>
</Project>
```

### 2.1 Required Properties

| Property                    | Value                          | Notes                                  |
|-----------------------------|--------------------------------|----------------------------------------|
| `TargetFramework`           | `net10.0`                      | Current LTS target (SDK 10.0.204)      |
| `AssemblyName`              | `FormatFactory.{Format}`       | PascalCase format name                 |
| `RootNamespace`             | `FormatFactory.{Format}`       | Must match AssemblyName                |
| `Nullable`                  | `enable`                       | Nullable reference types required      |
| `ImplicitUsings`            | `enable`                       | Standard implicit usings               |
| `GenerateDocumentationFile` | `true`                         | XML doc comments enforced              |
| `AllowUnsafeBlocks`         | `false`                        | No unsafe code without waiver          |
| `TreatWarningsAsErrors`     | `false`                        | May be set to `true` for mature libs   |

### 2.2 Cross-Format References

When a format library exports to another format, use `<ProjectReference>`:

```xml
<ItemGroup>
  <ProjectReference Include="../csv/FormatFactory.Csv.csproj" />
  <ProjectReference Include="../html/FormatFactory.Html.csproj" />
</ItemGroup>
```

Do NOT use NuGet package references for sibling Format Factory libraries. Always
use project references to keep the dependency graph local and build-time verifiable.

### 2.3 Version Scheme

- `0.1.0-tier0` — initial implementation, pre-release
- `0.1.0` — first stable release (post Gate 11 approval)
- SemVer rules apply after 1.0.0

## 3. Namespace Convention

```
FormatFactory.{Format}             — root namespace (Parser, Writer, Document)
FormatFactory.{Format}.Model       — supporting model classes
FormatFactory.{Format}.Spec        — specification-aligned classes
FormatFactory.{Format}.Exceptions  — exception types
```

All public types MUST reside within these namespaces. Internal helpers may use
sub-namespaces but MUST NOT be exposed in the public API.

---

## 4. Model Purity

### 4.1 Document Classes

The `{Format}Document.cs` class is a pure data container:

- NO file I/O (no `File.ReadAllText`, no `Stream` operations)
- NO network calls
- NO side effects in property getters or setters
- Pure data with typed properties and collections
- May contain computed properties derived from its own state

### 4.2 Parser Responsibility

`{Format}Parser.cs` owns ALL deserialization:

- Accepts file paths, streams, or string content
- Returns a fully populated `{Format}Document` instance
- Throws `{Format}DocumentException` (or subclass) on malformed input
- Static methods preferred: `{Format}Parser.Parse(string path)`

### 4.3 Writer Responsibility

`{Format}Writer.cs` owns ALL serialization:

- Accepts a `{Format}Document` and writes to file, stream, or returns string
- Static methods preferred: `{Format}Writer.Write({Format}Document doc, string path)`
- Round-trip fidelity: `Parse(Write(doc))` should produce an equivalent document

### 4.4 Exporter Responsibility

`{Format}{Target}Exporter.cs` converts between formats:

- Accepts a `{Format}Document`, returns target format output
- Each exporter handles exactly one target format
- Delegates to the target format's Writer when a project reference exists
- Static methods preferred: `{Format}{Target}Exporter.Export({Format}Document doc, string path)`

## 5. LOC and Complexity Caps

The same caps that apply to Python source apply to .NET source:

| Metric              | Cap   | Enforcement                               |
|---------------------|-------|-------------------------------------------|
| Lines of code       | 800   | Per file, measured by line count           |
| Functions / methods | 60    | Per file, public + private combined        |

These caps are tracked in `registry/source-structure-baseline.json`. Files that
exceed caps are recorded in `known_violations` with frozen `baseline_loc_cap` and
`baseline_functions_cap` values. The `baseline_loc_cap` is write-once (NEVER
increased). Only the `loc` field is mutable.

When a file approaches the cap, extract helpers into the `Model/` directory or
split into focused partial classes.

## 6. XML Documentation

All public API members MUST have XML documentation comments:

```csharp
/// <summary>
/// Parses a FODS file from the given path and returns the document model.
/// </summary>
/// <param name="path">Absolute or relative path to the .fods file.</param>
/// <returns>A fully populated <see cref="FodsDocument"/>.</returns>
/// <exception cref="FodsDocumentException">
/// Thrown when the file is missing or contains malformed XML.
/// </exception>
public static FodsDocument Parse(string path)
```

- `<summary>` is required on every public type and member.
- `<param>` is required on every parameter.
- `<returns>` is required on non-void methods.
- `<exception>` is required when the method can throw.
- `GenerateDocumentationFile` in the `.csproj` enforces compile-time warnings.

## 7. Exception Hierarchy

Each format defines its own exception type in `Exceptions/`:

```csharp
namespace FormatFactory.Fods.Exceptions;

/// <summary>
/// Thrown when a FODS document cannot be parsed, validated, or written.
/// </summary>
public class FodsDocumentException : Exception
{
    public FodsDocumentException(string message) : base(message) { }
    public FodsDocumentException(string message, Exception inner) : base(message, inner) { }
}
```

Rules:
- Inherit from `System.Exception` (not `ApplicationException`).
- Provide both `(string)` and `(string, Exception)` constructors.
- Parser and Writer MUST throw format-specific exceptions, not raw `Exception`.
- Do NOT catch and swallow exceptions silently.

## 8. Build Requirements

### 8.1 Individual Project Build

Every format library MUST build independently:

```bash
dotnet build src/net/{format}/FormatFactory.{Format}.csproj
```

No `.sln` file is required. The CI pipeline builds each project individually.

### 8.2 Restore and Clean

```bash
dotnet restore src/net/{format}/FormatFactory.{Format}.csproj
dotnet clean src/net/{format}/FormatFactory.{Format}.csproj
```

### 8.3 Build Artifacts

Build output goes to `bin/` and `obj/` within the project directory. These
directories are git-ignored. Do NOT commit build artifacts.

## 9. Testing

### 9.1 Test Project Location

Test projects live at:

```
tests/net/{format}/FormatFactory.{Format}.Tests.csproj
```

Existing test directories: `csv`, `fods`, `fodt`, `html`, `markdown`, `ndjson`,
`netpbm`, `tsv`, `txt`, `zst`.

### 9.2 Test Execution

```bash
dotnet test tests/net/{format}/FormatFactory.{Format}.Tests.csproj
```

All tests MUST pass before a sprint can be marked ACCEPTED.

### 9.3 Test Naming

Test classes: `{Format}{Feature}Tests.cs`
Test methods: `{MethodUnderTest}_{Scenario}_{ExpectedResult}()`

Example:
```csharp
public class FodsParserTests
{
    [Fact]
    public void Parse_ValidFile_ReturnsDocument() { ... }

    [Fact]
    public void Parse_MissingFile_ThrowsFodsDocumentException() { ... }
}
```

### 9.4 Test Independence

- Tests MUST NOT depend on execution order.
- Tests MUST NOT share mutable state.
- Use temporary files for I/O tests; clean up in `Dispose()`.

## 10. Coding Conventions

### 10.1 C# Style

- Follow Microsoft's C# coding conventions.
- Use file-scoped namespaces (`namespace X;` not `namespace X { }`).
- Use primary constructors where appropriate (C# 12+).
- Prefer `readonly` fields and `init` properties for immutable data.
- Use pattern matching over type-checking casts.

### 10.2 Nullability

With `<Nullable>enable</Nullable>`:
- All reference types are non-nullable by default.
- Use `?` suffix for nullable references: `string? optionalName`.
- Do NOT suppress nullable warnings with `!` except in test code.
- Validate arguments with `ArgumentNullException.ThrowIfNull()`.

### 10.3 Async

- Expose async methods for I/O-bound operations when practical.
- Name async methods with `Async` suffix: `ParseAsync()`.
- Accept `CancellationToken` as the last parameter.
- Do NOT use `async void` outside event handlers.

## 11. Spec QName Alignment

Every model class that represents a specification-defined concept MUST declare its
`spec_qname` mapping:

```csharp
/// <summary>
/// Maps to spec QName: table:table-cell (ODF Table namespace).
/// </summary>
public class FodsCell
{
    // ...
}
```

The mapping is recorded in `shared/qname-registry/{format}.yaml` with fields:
- `qname` — the canonical spec QName (e.g., `table:table-cell`)
- `canonical_class` — the spec-aligned class name
- `facade_names` — format-prefixed convenience names (e.g., `FodsCell`)
- `dotnet_file` — path to the .NET implementation file

Facade classes (format-prefixed names like `FodsCell`) belong in `Model/` or
`Spec/` and MUST reference the canonical spec class. Do NOT use format-prefixed
names as primary implementation targets.

## 12. Cross-Format Export Pattern

When a format supports export to another format:

1. Create `{Format}{Target}Exporter.cs` in the format's project root.
2. Add a `<ProjectReference>` to the target format's `.csproj`.
3. The exporter accepts a `{Format}Document` and produces target output.
4. Delegate to the target format's Writer for actual serialization.

Example (FODS to CSV):
```csharp
public static class FodsCsvExporter
{
    public static void Export(FodsDocument document, string outputPath)
    {
        // Transform FODS model to CSV model
        // Delegate to CsvWriter for serialization
    }
}
```

## 14. Checklist for New Format Libraries

When adding a new .NET format library:

- [ ] Create `src/net/{format}/FormatFactory.{Format}.csproj` per Section 2
- [ ] Create `{Format}Parser.cs`, `{Format}Document.cs`, `{Format}Writer.cs`
- [ ] Create `Exceptions/{Format}DocumentException.cs`
- [ ] Create `Model/` directory for supporting classes
- [ ] Create `Spec/` directory for spec-aligned hierarchy
- [ ] Create `README.md` for NuGet package
- [ ] Create test project at `tests/net/{format}/`
- [ ] Verify `dotnet build` passes
- [ ] Verify `dotnet test` passes
- [ ] Add QName entries to `shared/qname-registry/{format}.yaml`
- [ ] Register in `registry/format-registry.yaml`
- [ ] Ensure all public members have XML documentation
- [ ] Verify LOC stays under 800 per file
