# Ruflo — Lane Coordination Model

## Lane Architecture

Format Factory uses 11 lanes (C0–C10) for parallel sprint execution.
Lane definitions are generated by the supervisor and consumed by Ruflo.

## Lane Definitions

| Lane | Owner Role | Primary Responsibility |
|------|-----------|----------------------|
| C0 | Coordinator | Integration, manifest authority, file ownership enforcement |
| C1 | Governance | Repo governance discovery, preflight |
| C2 | TaskcardModel | Taskcard schema, state model |
| C3 | Supervisor | Supervisor architecture, memory sync |
| C4 | Scripts | Deterministic scripts, replay, contradiction detection |
| C5 | PromptSchema | Prompts, schemas, next-sprint generation, gate classifier |
| C6 | TM | Task Master integration contract |
| C7 | Ruflo | Ruflo integration contract |
| C8 | Security | Security scan, no-paid-API verification |
| C9 | Rollback | Rollback/recovery model |
| C10 | Verification | Evidence bundle, final verdict |

## File Ownership

Every file in a sprint belongs to exactly one lane.
No two lanes may write the same file.

The supervisor generates `overlap_check_passed: true` in `next-ruflo-lanes.json`
only after verifying no file ownership conflicts.

### Overlap Check Procedure

Before issuing any lane assignments:
1. Build the planned file ownership matrix from `next-ruflo-lanes.json`
2. Verify: every file appears in exactly one lane's `allowed_files`
3. Verify: no file appears in another lane's `allowed_files`
4. Any conflict: coordinator serializes the conflicting lanes (no parallel execution)

### Coordinator Serialization Rule

If Lane A and Lane B both need the same file:
1. Coordinator assigns file to whichever lane needs it first
2. Other lane must wait for coordinator merge
3. Lane outputs go to lane-specific files first
4. Coordinator merges after both lane evidences pass

## Coordinator Protocol (Lane C0)

The coordinator runs after all lane evidence is available:

1. Read preflight report before issuing any assignments
2. Verify file ownership matrix for no-overlap
3. Issue C1+C2 in parallel (no file conflict)
4. After C1: issue C3 (depends on C1 governance facts)
5. After C2: issue C4+C5 in parallel
6. After C3+C4+C5: issue C6+C7 in parallel
7. After C6+C7: issue C8+C9 in parallel
8. After C8+C9: issue C10 (final verification + evidence)
9. After each lane: verify acceptance criteria before marking TC done
10. If any lane blocks: re-assign to next available parallel slot; log in coordinator report
11. Emergency stop: halt all lanes on any forbidden condition

## Lane Status Lifecycle

```
pending → in_progress → completed
                     → blocked (external dependency)
                     → evidence_blocked (evidence failed)
```

All lane statuses are non-authoritative. Format Factory gate status is authoritative.

## Non-Authoritative Requirement

All lanes must carry `non_authoritative: true`.
A lane completing its work does NOT approve any Format Factory gate.

Validation: `validate_dual_orchestration_bridge.py` RULE-3 checks every lane.

## Emergency Stop Conditions for Lanes

Halt all lanes immediately if:
1. `.vscode/mcp.json` appears (MODE 0-3)
2. `.taskmaster/` appears in repo root (MODE 0-3)
3. `.ruflo/` or `.swarm/` appears in repo root (MODE 0-3)
4. Any validator in `tools/evidence/` or `tests/evidence/` is modified
5. AGENTS.md, GOVERNANCE.md, master-plan.md, or registry is modified
6. Any R78 untracked file is modified
7. Any real API key appears in any file
8. Daemon process starts unexpectedly

On emergency stop: log in `reports/dual-orchestration-supervisor-e2e/stop-gate-log.md`,
halt all work, report to user.
