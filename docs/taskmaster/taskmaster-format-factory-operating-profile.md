# Task Master AI — Format Factory Operating Profile

## Role in Architecture

Task Master AI is Layer 3 in the 5-layer architecture:

```
Layer 1: Format Factory Repo (AUTHORITY)
Layer 2: Local Supervisor Control Plane
Layer 3: Task Master AI  ← HERE (task graph / state engine)
Layer 4: Ruflo (lane/swarm coordination)
Layer 5: Claude Code (executor)
```

Task Master is the **task graph and state memory** layer.
It does NOT have authority over Format Factory gates or evidence.

## What TM Is Allowed to Do

- Maintain a task graph with dependencies and status
- Export task lists for Ruflo lane assignment
- Track which tasks are done, pending, blocked, evidence_blocked
- Provide task context to Claude Code sessions
- Import supervisor-generated task exports

## What TM Is NOT Allowed to Do

- Close Format Factory gates (gate closure requires human approval)
- Override evidence validators
- Mark tasks done in a way that implies gate approval
- Generate sprint prompts (that is the supervisor's role)
- Push or merge code
- Modify AGENTS.md, GOVERNANCE.md, master-plan.md, registry

## Activation by Mode

| Mode | TM Usage |
|------|----------|
| MODE 0-2 | None — schema validation of exports only |
| MODE 3 | Dry run — version check (`npm show task-master-ai version`) + import test |
| MODE 4+ | Active — MCP server registered (requires human approval) |

## CLI Behavior Note

`task-master-ai` CLI starts an MCP server when invoked. It does NOT support `--version`
or `--help` flags in the usual sense (both start the MCP server). Use:

```bash
npm show task-master-ai version    # Get version from npm registry
```

To check installed version:
```bash
npm list task-master-ai --depth=0  # Local installation
npm list -g task-master-ai         # Global installation
```

Default tool mode: **core** (7 tools). Extended surface available via MCP configuration.

## .taskmaster/ Directory Policy

The `.taskmaster/` directory must NOT exist in MODE 0-3.
If found unexpectedly: halt all lanes, quarantine, report to user.

In MODE 4+: `.taskmaster/` is created and managed by TM.
It must be listed in `.gitignore` (private local state).

## State File: .taskmaster/tasks/tasks.json

This file is TM's authoritative task graph. It is:
- Non-authoritative (does not override FF)
- Rebuilt from supervisor exports each sprint
- Never committed (gitignored)
- Backed by supervisor-generated `next-sprint-taskmaster.json` (tracked)

## Integration with Ruflo

TM exports the task list; Ruflo assigns tasks to lanes.
Neither TM nor Ruflo has authority. Both are coordination tools.

`next-sprint-taskmaster.json` → TM state
`next-ruflo-lanes.json` → Ruflo lane configuration

Both are generated by `generate_supervisor_packet.py` from supervisor evidence review.

## Failure Recovery

If `.taskmaster/tasks/tasks.json` is corrupt or inconsistent:
1. Delete `.taskmaster/` directory
2. Re-run `supervisor_loop.py export-taskmaster`
3. Re-import the clean export

TM state is always recoverable from the supervisor-generated export.
The supervisor-generated export is always recoverable from the evidence bundle.
