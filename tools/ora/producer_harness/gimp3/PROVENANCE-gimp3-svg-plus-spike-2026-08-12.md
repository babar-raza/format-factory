**Status: ACCEPTED_WITH_CHANGES (2026-08-12).** Independent adversarial
review (fresh agent, no prior conclusion stated, independently re-ran the
oracle and re-fetched GIMP's own live source) confirmed the pixel
evidence is real and the MISMATCH verdict is correct, but found 2 real
issues, both repaired in this revision: (1) the "source-only" expected-

(2) the root-cause claim overstated certainty — GIMP's own quoted C

("current GIMP 3.x for svg:plus"). Result: **empirically confirmed

## Pre-execution source inspection (per this session's own directive:
"First inspect the actual current OpenRaster plugin source")

Fetched GIMP's own current `master` branch `plug-ins/python/file-openraster.py`
from `gitlab.gnome.org/GNOME/gimp` directly, then independently
re-confirmed the installed image's own copy has an identical mapping
(extracted `/usr/lib/gimp/3.0/plug-ins/file-openraster/file-openraster.py`
from the built container and grepped it directly, not merely trusting
the upstream master branch matches what shipped). Both agree:

```python
layermodes_map = {..., "svg:plus": Gimp.LayerMode.ADDITION, ...}
```

`svg:dst-in`, `svg:dst-out`, `svg:src-atop`, `svg:dst-atop` are **absent**
from this map in GIMP's own current, official source — confirming the
already-established GIMP 2.10 finding (no Porter-Duff-operator selection
in GIMP's own layer-mode system) is not a version-specific gap; it is
architectural and applies to GIMP 3.x too. Not retested empirically here
since GIMP's own source already shows no attempted mapping exists to test.

Also fetched GIMP's own current `app/operations/layer-modes/gimpoperationlayermode-blend.c`
and read `gimp_operation_layer_mode_blend_addition` (the non-legacy
Addition mode's real C implementation) *before* running anything:

```c
if (in[alpha] != 0.0f && layer[alpha] != 0.0f)
  { for (c = 0; c < alpha; c++) comp[c] = in[c] + layer[c]; }
comp[alpha] = layer[alpha];
```

This predicted a specific defect: when the backdrop's own alpha is zero,
the color channels are never written (left at whatever `comp` was
initialized to), unlike the correct Porter-Duff Lighter formula (`Fa=Fb=1`
at any alpha, including alpha_b=0 — the source should show through
alone). This prediction was verified, not assumed, per below.

## Path A — native creation, GIMP's own current Addition mode, exported

`LAYER-MODE-ADDITION=33` (non-legacy; confirmed via Script-Fu reflection,
matching the plugin's own forward mapping) used to create the exact
discriminating fixture (destination (230,60,40) alpha 153/255 at
(0,0)-(20,20); source (40,120,230) alpha 128/255 at (12,12)-(32,32), on a
32×32 canvas — identical to the already-committed
`composite-porterduff-lighter.ora`), exported via `file-openraster-export`.

**Real, disclosed GIMP 3.0.4 writer defect found**: the exported
`<image>` element omits the required `version` attribute entirely
(`<image w="32" h="32">`, confirmed via direct `stack.xml` inspection).
format-factory's own `ReadMode.STRICT` correctly refuses this
(`OraValidationError: <image> is missing the required 'version'
attribute`); `ReadMode.TOLERANT` accepts it with a named recovery action
(`"root <image> had no 'version' attribute..."`). This is a genuine GIMP
3.0.4 export non-conformance, not a fixture or format-factory issue —
disclosed, not patched around or hidden. `gimp3-native-svg-plus.ora`
preserved unmodified.

## Path B — import canonical strict `.ora`, render, export PNG

`composite-porterduff-lighter.ora` (already committed, already confirmed

## Pixel comparison (exact, at the discriminating sample points)

| Point | GIMP 3.0.4 (RGBA) | Oracle expected (RGBA) | Match |
|---|---|---|---|
| dest-only (5,5) | (230,60,40,153) | (230,60,40,153) | exact |
| source-only (25,25) | **(0,0,0,0)** | (40,120,230,128)† | **MISMATCH** |
| overlap (16,16) | (231,104,173,**153**) | (158,96,139,**255**)‡ | **MISMATCH** |
| transparent (2,28) | (0,0,0,0) | (0,0,0,0) | exact |

† the source layer's own straight (non-premultiplied) RGBA, unchanged —
correct per `Fa=Fb=1` at `alpha_b=0`
(`porter_duff_coeffs('Lighter', 0.502, 0.0) == (1.0, 1.0)`). **Correction**:
an earlier draft of this table stated `(20,60,115,128)` here — the
premultiplied *intermediate* value, not the final straight-RGBA result —
presented as independently confirmed when it had not actually been
regenerated by invoking `composite_oracle.py`. Caught by an independent
review that re-ran `composite(Pixel(0,0,0,0), source, 'Normal',
'Lighter')` directly and got `(40,120,230,128)`; corrected here rather
than left standing. The MISMATCH verdict itself is unaffected — GIMP's
real `(0,0,0,0)` output matches neither the wrong nor the corrected value.

‡ **Second correction (2026-08-12, fourth continuation)**: the original
value shown here, `(143,87,127,255)`, was itself computed by a genuinely
buggy `composite_oracle.py` — `composite_porter_duff()` divided by the
Lighter operator's own *unclamped* combined alpha (1.102, since
0.502+0.6 > 1) when unpremultiplying color, rather than clamping to 1.0
first. Found by comparing against GEGL's own real, independent
`svg:plus` implementation (`operations/generated/plus.c`), whose real
output for this identical fixture, `(158,96,139,255)`, did not match
this oracle's own prior output; hand-verified against the Porter & Duff
(1984) formula directly and confirmed GEGL was right. Fixed in
`composite_oracle.py` (see its own updated docstring for the full
account) with 3 new regression tests
(`tests/tools/test_ora_composite_oracle.py`). The `MISMATCH` verdict for
GIMP 3.0.4 is unaffected either way (GIMP's real alpha=153 matches
neither 255 value); this correction affects only the cited "expected"
RGB figures, not any obligation-level conclusion.

**Root cause — confirmed for the RGB channels, genuinely unexplained for
alpha; stated precisely rather than claimed as fully solved**: GIMP's own
`gimp_operation_layer_mode_blend_addition` (quoted above, verbatim from
GIMP's own live GitLab `master`) explains the RGB-channel behavior at the
source-only point exactly — its `if (in[alpha] != 0.0f && layer[alpha]
!= 0.0f)` guard skips writing `comp[c]` for `c < alpha` whenever the
backdrop's alpha is zero, so no color is ever written there. It does
**not**, on its own, explain the observed alpha=0 at that same point:
the quoted function's own `comp[alpha] = layer[alpha]` line is
unconditional, which would predict alpha≈128 (the source layer's own
alpha) at that point, not 0. Some other stage in GIMP's own compositing
pipeline (not identified in this spike — a genuine gap in this
investigation, not glossed over) evidently produces the final alpha=0.
The empirically observed MISMATCH itself is real and directly measured,
independent of this open question about which exact code path produces
it; the RGB-channel mechanism is confirmed, the alpha mechanism is not.

## Verdict

**`svg:plus` does NOT qualify as GIMP-3.x-covered.** This is an
empirically confirmed mismatch, not merely "GIMP cannot test it" (GIMP
3.x *can* now attempt `svg:plus`, unlike the complete absence of any
mapping for the 4 Porter-Duff operators) — GIMP 3.0.4's own current
Addition-mode implementation is genuinely, verifiably non-conformant with
the Porter-Duff Lighter formula at the exact points that matter (zero-
backdrop-alpha handling and premultiplied-alpha clamping). A single
GIMP-3.x pass here would not have counted as the "second" qualifying
implementation for `svg:plus` per this session's own directive regardless
("A single successful jsora result only changes it from zero to one
unless GIMP 3.x or another implementation also passes") — the actual
result is that GIMP 3.x does not pass at all, so it contributes zero
toward this specific gap. The other 10 already-single-producer operations
were not retested against GIMP 3.x, per this session's own directive
("do not rerun the full matrix merely because a newer version exists")
and because GIMP's own current source for the 4 missing Porter-Duff
operators shows no attempted mapping to test, and the 6 non-conformant
blend functions were not source-inspected for a plausible fix in this
GIMP release (no changelog evidence of a fix was found or searched for,
disclosed as not attempted rather than assumed unchanged).
