## Objective

Formalize the governance contract for the AI-generated requirements pipeline so that:

1. Requirements regeneration is triggered only when input sources change (stale-detection)
2. AI usage is logged in each generation run
3. Verifier review (Lane R5) is always separate from generation (Lane R3/R4)
4. Schema validation always runs after generation (Lane R2)
5. ACCEPTED_FOR_VERTICAL_SLICE status is only granted after verifier approval
6. Conversion requirements remain future-scoped in all initial sprints

## Pipeline Governance Rules

### Rule 1: Stale Detection
- Every generation run records `input_source_hashes` for all 10+ input sources
- If any input hash changes, regeneration is REQUIRED before implementation may proceed
- Stale artifacts must be clearly marked — no silent use of outdated requirements

### Rule 2: AI Usage Logging
- Every generation run records `model_tool` (AI model used or "AI_UNAVAILABLE")
- `generator_version` must be incremented on any pipeline design change
- AI synthesis (Stage 11) is labeled `source_type: AI_PROPOSAL` in output — never pre-accepted

### Rule 3: Verifier Separation
- Lane R5 (verifier) MUST run in a separate pass from Lane R3/R4 (generation)
- DEC-034 authorization governs whether inline or separate session is required
- Verifier findings are recorded in `verifier-review.yaml` per format
- A requirement may only advance to ACCEPTED_FOR_VERTICAL_SLICE if verifier verdict is
  VERIFIED_ACCEPTED or VERIFIED_ACCEPTED_WITH_NOTES

### Rule 4: Schema Validation Gate
- LANE R2 (schema validation) must produce REQUIREMENTS_SCHEMA_VALIDATION: PASS before
  any implementation lane (C-F) may consume the generated requirements
- Failure is a blocker — no workarounds permitted

### Rule 5: Conversion Requirements
- All conversion requirements (PDF, HTML, PNG, related formats) are marked `sprint_scope: future`
- They may NOT be marked ACCEPTED_FOR_VERTICAL_SLICE in any initial sprint
- They enter implementation only when a dedicated conversion sprint is authorized

### Rule 6: No Manual Authoring
- Requirements in `generated-requirements/` must be generated by the pipeline
- If manual edits are made, they must set `manually_edited: true` per the pipeline spec
- Manual edits are exceptions and must be justified in the verifier-review.yaml
