## Diagnosis

### What the first analysis found (symptoms)
Monolithic Python files (fods_analytics.py 1103 LOC, xcf_image_metrics.py 104 fn, zst_codec.py
mixed responsibilities, abw/word_document.py 101 fn). C# partial-class files at or near LOC
caps. 165 validators deployed.

### What the deep investigation found (structural failures)

The machinery appears to work — 165 validators, a production standard, a baseline registry, an
evidence grader, a sprint loop. But four structural failures cause inconsistent results across reruns:

**Failure 1: Validators are tested for registration, not detection.**
`test_governance_validators.py` asserts `expected_count = 165`. It uses synthetic fixtures.
No test runs any validator against an actual file in `src/`. V35 (monolith detection), V66
(multi-responsibility), V40 (source architecture) — all pass their tests while the files they
are supposed to catch sit undetected in `src/python/`. If a validator silently degrades (wrong
regex, path mismatch), it still counts as 1 in 165. The sprint continues as if governance is
enforced. This is the root cause of "validators say clean but monoliths accumulate."

**Failure 2: The source baseline is an amnesty list, not a burn-down queue.**
`registry/source-structure-baseline.json` has 100+ entries. Write-once `baseline_loc_cap`
is the ceiling. But: V40 emits WARN (non-blocking) for ALL existing violations, and FAIL only
for NEW files. A file in `known_violations` can grow past `baseline_loc_cap` — it still only
WARNs. No removal mechanism exists. No `heal_deadline`, no automated escalation. An entry
added in 2025 for `FodtDocumentExtendedApis.cs` (2,944 LOC) will still be there in 2027
unless manually removed. The baseline is permanent amnesty masquerading as tracked debt.

**Failure 3: Evidence grading does not verify that code improved.**
`grade_declared_work.py` checks: does a test file exist? does it contain `assert`? does an
evidence file exist? It never checks whether the declared files actually changed in the git
history, whether LOC reduced, whether function counts dropped, or whether a violation was
removed from the baseline. A sprint can write `"refactored zst_codec.py from 1073 → 800 LOC"`
in its declaration with passing tests and get graded ACCEPTED — even if `zst_codec.py` is
unchanged. The `changed_files` field in declarations is worker-supplied with no cross-check.

**Failure 4: Sprint selection is violation-blind.**
`next-sprint.md` is generated by the supervisor pipeline without any signal from the count or
age of `known_violations`. The pipeline can select a product deepening sprint (new analytics
functions, new format features) even when 100+ files are in the violation baseline. There is
no algorithmic pressure to prioritize healing over new work. Healing only happens if the sprint
prompt explicitly says so. Organic sprints leave violations indefinitely.

### What must NOT be changed
- The 165 existing validators are broadly correct in intent. The problem is their test coverage
  and enforcement gaps, not their logic.
- The `baseline_loc_cap` write-once policy is correct — it prevents cap inflation. Don't change it.
- The Production Library Standard v2 is thorough. It needs structural additions, not a rewrite.
- The sprint closeout loop (declaration → autonomous-cycle → check_continuation) is sound.
  The fixes go inside the grader and schema, not the loop architecture.

## Solution Design

The four failures require four targeted structural fixes, plus the surface-level validator
additions. These are ordered by impact on consistency across reruns.

### Fix 1 — Detection tests (addresses Failure 1)

Add a second test class `TestValidatorDetection` in `tests/supervisor/test_governance_validators.py`
containing ~10 tests that run specific validators against real files in `src/`. These tests
verify that validators fire on actual violations, not just on synthetic fixtures.

Design rules for detection tests:
- Each test creates a minimal evidence declaration with a real `src/` file in `changed_files`
- Runs the specific validator function directly (not the full runner)
- Asserts the result is `WARN` or `FAIL` (not `PASS`) for a known violating file
- Asserts `PASS` for a file that is clean (regression guard)
- Tests are parametrized by file path so they auto-fail if the file is healed (which is the
  intended behavior — healing should make governance tests go green, not red)

Tradeoff: detection tests are coupled to current file state. If `fods_analytics.py` is split,
`test_v144_fires_on_fods_analytics` will fail. That is the intended signal: update the test
when the violation is healed. This coupling is a feature, not a bug — it creates accountability.

Risk: If detection tests use real files that change due to unrelated work, they may produce
unexpected failures. Mitigation: gate detection tests behind a pytest mark (`@pytest.mark.real_src`)
so they can be excluded from fast CI and included in governance CI.

### Fix 2 — Baseline burn-down schema (addresses Failure 2)

Extend `registry/source-structure-baseline.json` schema to add:
- `heal_deadline: "YYYY-MM-DD"` (optional; absence means indefinite)
- `heal_status: "pending" | "in_progress" | "complete"` (default: pending)
- `heal_sprint: "TC-HEAL-*"` (which sprint taskcard owns the healing)

Add a new validator **V150** (`validate_baseline_deadline_expired`) that:
- Scans `known_violations` entries with `heal_deadline` set
- For entries where `heal_deadline < today AND heal_status != "complete"`:
  - Emits WARN with the file path, deadline, and responsible `heal_sprint`
- Does NOT block (WARN only) — deadlines slipping is bad but must not hard-stop all sprints
- DOES appear in the `rework_items` of the continuation signal, creating soft pressure

Add the top 5 HIGH severity entries from the gap inventory to the baseline with
`heal_deadline: "2026-10-01"` and corresponding `heal_sprint` references.

Tradeoff: WARN not FAIL means persistent debt doesn't hard-block. The alternative (hard-block
after deadline) would make every sprint fail once one deadline slips — too fragile. WARN with
rework_item creates friction without paralysis.

Limit: This mechanism only works if heal_deadlines are actually set. Entries without a
deadline remain under indefinite amnesty. The fix scopes to the 5 highest-priority entries
now; future sprints should add deadlines as they triage violations.

### Fix 3 — Evidence before/after quality metrics (addresses Failure 3)

Two changes:

**3a. Extend evidence-declaration.schema.json** to add a `code_quality_delta` block
for PRODUCT_SOURCE work items that target files in `known_violations`:
```yaml
code_quality_delta:
  file: src/python/{format}/{file}.py
  loc_before: 1073
  loc_after: 650
  fn_count_before: 25
  fn_count_after: 15
  violation_removed: true   # means removed from known_violations after this sprint
```
This is REQUIRED for declared PRODUCT_SOURCE items where `target_files` contains a
`known_violations` entry. Optional for all other PRODUCT_SOURCE items.

**3b. Add Phase 13 check in `tools/supervisor/sprint_executor_validate.py`**:
- For each PRODUCT_SOURCE work item with a `known_violations` file in `target_files`,
  check that `code_quality_delta` is present
- If present, verify: `loc_after < loc_before` OR `fn_count_after < fn_count_before`
  (at least one metric must improve; zero-change declarations fail this check)
- If `violation_removed: true`, check that the file is actually absent from the baseline
  (read baseline JSON and verify the entry is gone or has `heal_status: "complete"`)
- Failure mode: WARN on missing `code_quality_delta`, FAIL on `violation_removed: true`
  when the baseline still shows the entry as non-complete

Tradeoff: This requires the sprint worker to manually supply `loc_before` / `loc_after`.
The values are not auto-computed from git. The grader verifies the claimed direction (after <
before) but not the exact numbers. Perfect verification would require git-integrated LOC
diffing, which is out of scope here. The fix makes false claims detectable (worker must lie
about specific numbers, not just omit them) while staying implementable in one sprint.

**3c. Add V151 (`validate_changed_files_present`)** — not full git diff cross-check (that
is too fragile mid-sprint) but a weaker check: for each file in `changed_files`, verify the
file exists on disk. Catches common mistakes (wrong path, deleted file declared as changed).
Status: WARN only.

### Fix 4 — Violation pressure in continuation signal (addresses Failure 4)

Extend `tools/supervisor/check_continuation.py` to compute and emit a `violation_pressure`
field in its JSON output:
```json
{
  "verdict": "CONTINUE",
  "violation_pressure": {
    "total_violations": 112,
    "past_deadline": 0,
    "high_severity": 5,
    "pressure_level": "LOW | MEDIUM | HIGH | CRITICAL"
  }
}
```
`pressure_level` rules:
- CRITICAL: any violation with `heal_deadline` expired
- HIGH: `total_violations > 100` OR `high_severity > 10`
- MEDIUM: `total_violations > 50`
- LOW: otherwise

The supervisor's `generate_next_sprint()` function reads `violation_pressure` and, when
level is HIGH or CRITICAL, inserts a healing sprint task at rank 1 in `next-sprint.md`
before any product deepening task. This is the algorithmic pressure mechanism.

Tradeoff: This requires the next-sprint generator to be modified. The current generator is
in `supervisor_loop.py` or a sub-module — the exact hook point must be verified during
execution. If the generator is not easily modifiable, a fallback is to add `violation_pressure`
to the continuation signal output only (for human visibility) without the task-ordering change.
Document this as a partial fix if the generator is not hookable.

# Phase 13: code_quality_delta validation
for item in declared_items:
    if item.type == "PRODUCT_SOURCE":
        for f in item.target_files:
            if f in known_violations:
                if "code_quality_delta" not in item:
                    yield Warning(f"PRODUCT_SOURCE targets known_violation {f} but lacks code_quality_delta")

### TC-GOV-LLE-007: Violation pressure in continuation signal
**Status: PENDING**

Extend `tools/supervisor/check_continuation.py` to output `violation_pressure` in its JSON
response, and extend the next-sprint generator to read it.

**Change 1: check_continuation.py output extension**
```python
def compute_violation_pressure(baseline_path):
    baseline = json.loads(Path(baseline_path).read_text())
    violations = baseline.get("known_violations", {})
    total = len(violations)
    today = datetime.now()
    past_deadline = sum(
        1 for v in violations.values()
        if "heal_deadline" in v and datetime.fromisoformat(v["heal_deadline"]) < today
        and v.get("heal_status", "pending") != "complete"
    )
    high_severity_count = sum(
        1 for v in violations.values()
        if v.get("loc", 0) > 900 or v.get("functions", 0) > 80
    )
    if past_deadline > 0:
        level = "CRITICAL"
    elif total > 100 or high_severity_count > 10:
        level = "HIGH"
    elif total > 50:
        level = "MEDIUM"
    else:
        level = "LOW"
    return {"total": total, "past_deadline": past_deadline,
            "high_severity": high_severity_count, "level": level}
```

## Honest Tradeoffs and Limits

| Decision | What it buys | What it doesn't buy |
|----------|-------------|---------------------|
| Detection tests coupled to current file state | Accountability: a violation being healed makes the test go green | Tests break when files change for unrelated reasons; need `real_src` mark to isolate |
| WARN not FAIL for V150 (deadline expiry) | No sprint paralysis when one deadline slips | Deadlines can slip indefinitely; WARN is friction not hard enforcement |
| Self-reported `code_quality_delta` metrics | Forces workers to commit to specific numbers | Cannot verify exact values without git-integrated before/after LOC computation |
| `violation_pressure` as advisory text in next-sprint.md | Creates systematic visibility of debt | Product deepening can still be chosen if the agent ignores the advisory |
| 7 new validators, not full V66 replacement | Fast to implement, no regression risk | V66's keyword-only detection gap persists; it may miss non-standard naming patterns |

These tradeoffs are acceptable for a single sprint. Each limit is a named, documented gap —
not a hidden assumption or an optimistic claim.
