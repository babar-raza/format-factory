## PART IV: SOLUTION ARCHITECTURE

### Design Principle (closed feedback loop)

```
DOM gap in gap-ledger.json
  → lane_selector.py picks Lane B for format (reads ledger counters)
  → sprint generator reads lane decision → orders DOM gaps first
  → sprint prompt instructs: declare deepening_lane: dom
  → agent executes DOM work (mutation API + roundtrip test)
  → evidence declaration carries deepening_lane: dom (or gap_id with -DOM-)
  → autonomous_cycle_extensions.update_lane_counters() increments lane_b_consecutive
  → dom_maturity_promoter.py runs behavioral proof tests
  → ledger lane_b_maturity advances when proof passes
  → lane_selector.py reads updated counts → selects correct lane next sprint
```

### What to preserve (do NOT rewrite)
- `lane_selector.py` — logic is correct; 7 modes are well-designed. Wire it in.
- `product-deepening-ledger.yaml` — structure is good; values need derivation, not manual setting.
- `policies.yaml §10` — FULL/PARTIAL/FLAT/METRICS_ONLY classification is correct.
- Gap ledger mechanism — 1,487 entries with priority scoring are valuable. Extend, don't replace.
- Existing roundtrip tests — foundation for mutation roundtrip extension.
- `dom_maturity_promoter.py` — structure is reusable; ADD behavioral proof runner.
- `update_lane_counters()` function body — logic is correct; add gap_id fallback as input preprocessing.

### What must be changed
1. `gap-ledger.json` — add DOM gap entries (new generator tool)
2. Sprint generation pipeline — call lane_selector.py, use output to order gaps
3. `dom_maturity_promoter.py` — add behavioral proof runner (behavioral over AST-only)
4. `autonomous_cycle_extensions/__init__.py` — add gap_id fallback in `update_lane_counters()`
5. `policies.yaml` — add `mutation_roundtrip_required: true` to `dom_d2_contract`
6. `src/python/fodt/models.py` + `writer.py` — add mutation API and `to_file()` method
7. `src/python/fods/models.py` + writer — add `FodsDocument.to_file()` method
8. New test files — mutation roundtrip tests for FODS and FODT
9. New proof definition files — `.supervisor/dom-proofs/fods.yaml` and `fodt.yaml`

## PART V: MACHINE STATE MODEL

### Parent TC States
```
PROPOSED → READY → IN_PROGRESS → CHILDREN_IN_PROGRESS → INTEGRATION_PENDING → VERIFIED → SCORED → CLOSED
                                                                                              ↓
                                                                                         REROUTED (score < 4/5)
```

### Child TC States
```
TODO → READY → IN_PROGRESS → IMPLEMENTED → VERIFIED → SCORED → CLOSED
                                                             ↓
                                                        REROUTED
```

### Micro-Step States
```
PENDING → READY → ACTIVE → COMPLETE
                         ↓
                    FAILED → (parent child TC → REROUTED)
                    BLOCKED → (escalate to parent, try alternate path)
```

### Reroute Rules
- Child TC scores < 4/5 → REROUTED; create new child TC with corrective action
- Micro-step FAILED → child TC enters REROUTED; do not proceed to next micro-step
- Parent TC cannot be VERIFIED until all children are CLOSED or REROUTED-and-replaced
